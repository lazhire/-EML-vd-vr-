0.6.9 性能分析与后续方向

当前路径：Unity/HG 渲染两眼 -> Texture2D.ReadPixels 同步读回 -> CPU 数据复制 -> OpenXR 独立 Vulkan device 上传 -> 提交。正常桌面合成仍在运行。
每眼 2560*2560、RGBA8、双眼原始数据为 52,428,800 字节/帧；假设 90 次新双眼提交/秒，单向有效像素量约 4.72 GB/s。回读和上传均有此量级的数据，加上中间 CPU 拷贝和同步。不是测得的 PCIe 带宽，也不是瓶颈已被定量确认。
像素量相对每眼1024增加6.25倍；3072增加9倍。FPS不按此倍数线性变化。

优先方向
1. 获取合法的游戏 Vulkan device/queue/image 与渲染完成同步，尽量同 GPU 内拷贝到 OpenXR 交换链，避免 GPU->CPU->GPU。
2. 若不能直通，探索可用的异步读回及有界缓冲。需要绑定图像对应的眼位/FOV/时间，不能拿上一帧图像配当前眼位，不能无限排队。
3. 大世界降低/复用桌面镜像渲染，菜单前恢复完整 UI 合成；当前不能简单关主相机，否则菜单会再次黑屏。
4. 之后才考虑单次立体/多视图、每眼剔除和后处理共享。自定义 HG 渲染管线不意味着开启 Unity XR 开关就能获得这些能力。
5. 逐项测量后选择眼分辨率、游戏阴影/体积效果、VD刷新率，不把提高进程优先级当作同步瓶颈修复。

新日志每约2秒输出 performance。eye_render_cpu_ms 是双眼 Render 调用墙钟时间；eye_readback_cpu_ms 包含同步等待和复制；upload_submit_cpu_ms 包括上传/交换链/围栏/end-frame 等子阶段，不应重复相加。
application_stereo_pairs_hz 是新双眼图像提交吞吐，不是头显刷新率/补帧率。菜单期间或代际切换后不可用的双眼计时返回 null。
数据并不包含 VD 网络/编码/解码延迟。未来定位应与 VD 的应用、编码、网络、解码读数一起看。
GPU直通未在本版实现，当前不能保证任何显卡在本MOD最高画质下稳定90/120FPS。
